# GET / POST service — HTTPS

Адрес после развёртывания: **https://82.202.139.43/**, стандартный порт **443**.
Frontend отсутствует: сервис принимает GET/POST и возвращает JSON.

## Запуск на публичном сервере

Запускайте проект **на машине, которой принадлежит IP 82.202.139.43**, либо на машине,
на которую проброшены порты этого IP. Нужны Docker Engine и Docker Compose с Linux containers.
Локальный запуск на другом компьютере не выпустит сертификат для этого публичного адреса.

Перед запуском:

- Разрешите входящие **TCP 80 и TCP 443 из интернета** в брандмауэре ОС и правилах
  облачного провайдера. Эти порты должны быть свободны для Caddy.
- При NAT перенаправьте оба порта на машину с Docker. Проверка сертификата должна
  попадать именно в Caddy из этого проекта.
- Серверу нужен исходящий доступ к DNS и HTTPS для загрузки образов и обращения к Let's Encrypt.

Изменения передаются через Git. Закоммитьте и отправьте их в свой репозиторий,
включая `server.js`, `Caddyfile`, `package.json`, `Dockerfile`, `.dockerignore` и `compose.yaml`.
Вся обработка запросов и запись файлов выполняются самим `server.js`.

Для первого запуска склонируйте репозиторий на сервер и перейдите в папку проекта.
Если репозиторий уже склонирован, сначала получите обновления:

```sh
git pull --ff-only
```

В папке проекта запустите:

```sh
docker compose config --quiet
docker compose up -d --build
docker compose logs -f https
```

Caddy автоматически запросит **доверенный сертификат Let's Encrypt для 82.202.139.43**.
До завершения выпуска HTTPS может быть недоступен. Успешная проверка ниже подтверждает,
что сервис работает и сертификату доверяет клиент. Выход из просмотра логов — Ctrl+C;
контейнеры продолжат работать.

```sh
curl -i https://82.202.139.43/health
```

Ожидается HTTP 200 и `{"status":"ok"}` **без `-k` / `--insecure`**.
При ошибках выпуска проверьте доступность портов, назначение IP и логи `https`.

Если раньше использовался `docker compose`, команда `up` пересоздаст старый сервис
и передаст порт 80 Caddy. Если старый контейнер запускали вручную через `docker run`,
сначала остановите именно его, чтобы освободить порты.

## Как устроен HTTPS

- Caddy принимает внешние соединения на **443** и передаёт запросы сервису `post-server:8080`
  по изолированной Docker-сети. Порт 8080 не публикуется на машине.
- Порт **80** обслуживает проверку сертификата и автоматическое перенаправление HTTP → HTTPS.
- Сертификат запрашивается у публичного Let's Encrypt с профилем `shortlived`,
  а не у локального центра сертификации. Для IP-сертификатов срок составляет около
  шести дней; Caddy автоматически продлевает сертификат. Держите контейнер `https`
  запущенным, а порты доступными для повторных проверок.
- Сертификаты, закрытые ключи и ACME-аккаунт хранятся в volume `post-server-caddy-data`.
  Они не включаются в образ и исходники. Состояние Caddy хранится в `post-server-caddy-config`.

Поддержка IP-сертификатов: [официальное описание Let's Encrypt](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability).
Настройка профиля: [документация Caddy](https://caddyserver.com/docs/caddyfile/directives/tls#acme).

## Тестовые запросы из Windows cmd

GET с параметрами:

```cmd
curl.exe "https://82.202.139.43/save?message=hello&id=123"
```

POST с JSON:

```cmd
curl.exe -X POST "https://82.202.139.43/" -H "Content-Type: application/json" -d "{\"message\":\"hello\",\"id\":123}"
```

Для пробелов и специальных символов используйте кодирование curl:

```cmd
curl.exe --get "https://82.202.139.43/save" --data-urlencode "message=hello world" --data-urlencode "id=123"
```

Поддерживается любой путь, включая `/`, `/save`, `/post`, `/webhook`.
Исключение — `GET /health` (включая параметры URL): он проверяет состояние без записи в журнал.
Остальные методы возвращают HTTP 405.

После записи запроса сервер возвращает HTTP 200:

```json
{"status":"ok","requestId":"уникальный UUID","receivedBytes":28}
```

При ошибке записи возвращается HTTP 500. Лимит тела по умолчанию — 1 МиБ, превышение — HTTP 413.
GET-параметры записываются в раздел «Параметры URL» как строки, повторяющиеся ключи — массивами:
`?tag=one&tag=two` → `{"tag":["one","two"]}`. У обычного GET `receivedBytes` равно 0,
поскольку данные передаются в URL, а не в теле. Каждый запрос создаёт новую запись.
Тело POST принимается без обязательной проверки JSON. Корректный JSON записывается
с отступами, остальной текст — отдельными строками. Если форматирование JSON меняет
значения больших чисел или повторяющиеся ключи, сохраняется исходный текст.

## Где находятся запросы

В контейнере **`post-server`** сервис сразу записывает три обычных текстовых файла:

| Файл | Содержимое |
| --- | --- |
| `/app/logs/service.log` | Служебные события и ошибки, без тел и параметров запросов |
| `/app/logs/get.log` | GET-запросы, разделённые на читаемые блоки |
| `/app/logs/post.log` | POST-запросы, разделённые на читаемые блоки |

Форматирование уже находится **в самих файлах**. Дополнительные программы,
скрипты просмотра и команды `node` для чтения не нужны.
Каждый блок содержит метод и URL, время UTC, ID, IP отправителя и соединения,
размер и кодировку тела, параметры URL, тело и заголовки. JSON выводится с отступами.
Например, фрагмент GET-запроса:

```text
Параметры URL:
  {
    "message": "hello",
    "id": "123"
  }
Тело:
  (пусто)
```

Если вы уже внутри `sh` контейнера **post-server**, читайте файлы обычными командами:

```sh
cat /app/logs/get.log
more /app/logs/post.log
tail -f /app/logs/service.log
```

В `more`: пробел — следующая страница, `q` — выход. Из `tail -f` выход — Ctrl+C.
Последние 100 строк POST-запросов или новые GET-запросы в реальном времени:

```sh
tail -n 100 /app/logs/post.log
tail -f /app/logs/get.log
```

На машине с Docker, из папки проекта, без входа в контейнер:

```sh
docker compose exec post-server cat /app/logs/get.log
docker compose exec post-server more /app/logs/post.log
docker compose exec post-server tail -f /app/logs/service.log
```

Контейнер **https** с рабочей папкой `/srv` — это Caddy; файлов запросов в нём нет.
Его служебные события и выпуск сертификатов смотрите через `docker compose logs -f https`.

Файлы находятся в прежнем volume **`post-server-logs`** и сохраняются при пересоздании
контейнера. GET/POST-файлы создаются после первого запроса соответствующего метода.
`/health` не записывается. Тела и параметры запросов не дублируются в служебном журнале
и консоли. `Authorization`, `Proxy-Authorization` и `Cookie` скрываются.

UTF-8 записывается текстом, остальные байты — Base64; кодировка указана в блоке запроса.
Управляющие символы отображаются как `\uXXXX`, чтобы они не меняли вид терминала.
IP отправителя берётся из заголовка `X-Real-IP`, который перезаписывает Caddy;
доверие к этому заголовку включено только для внутреннего backend в Compose.

Скопировать читаемые файлы из контейнера в текущую папку:

```sh
docker compose cp post-server:/app/logs/get.log ./get.log
docker compose cp post-server:/app/logs/post.log ./post.log
docker compose cp post-server:/app/logs/service.log ./service.log
```

Старые файлы `requests.jsonl`, `get.jsonl` и `post.jsonl`, если они уже были созданы,
остаются нетронутыми. Новые запросы идут только в `get.log` и `post.log`.
Файлы в `/app/logs` не ротируются автоматически. Консольные логи Docker ограничены
тремя файлами по 10 МиБ на контейнер. HTTP 200 выдаётся только после записи запроса.

## Обновление и остановка

После отправки новых изменений в Git выполните на сервере в папке проекта:

```sh
git pull --ff-only
docker compose up -d --build
docker compose exec https caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
docker compose ps
```

Команда `reload` применяет обновлённый `Caddyfile`: изменение файла в Git само
по себе не заставляет уже работающий Caddy перечитать конфигурацию.

Остановка:

```sh
docker compose down
```

Обычный `down` сохраняет журнал и сертификаты. **`down --volumes` удалит их**.
Для переноса на другой сервер нужны файлы проекта и, если нужно сохранить историю
и сертификаты, отдельные резервные копии volumes обоих сервисов.

## Локальная разработка

`node server.js` запускает только HTTP backend, без публичного HTTPS. Для локальной
проверки на loopback из cmd (Node.js 22+; внешних npm-зависимостей нет):

```cmd
set HOST=127.0.0.1
set PORT=8080
node server.js
```

Проверка backend: `curl.exe "http://127.0.0.1:8080/health"`.
Публичный HTTPS запускается через Docker Compose и Caddy, как описано выше.

| Переменная backend | По умолчанию | Назначение |
| --- | --- | --- |
| `HOST` | `0.0.0.0` | Адрес прослушивания |
| `PORT` | `80` (прямой запуск), `8080` (Docker) | Внутренний HTTP-порт |
| `MAX_BODY_BYTES` | `1048576` | Лимит тела в байтах |
| `LOG_DIR` | `logs/` рядом с сервером, `/app/logs` в Docker | Папка для `service.log`, `get.log` и `post.log` |
| `LOG_FILE` | не задана | Совместимость со старой настройкой: при отсутствии `LOG_DIR` используется папка этого пути; сам общий файл больше не дополняется |
| `TRUST_PROXY` | `false` (прямой запуск), `true` (Compose) | Доверять `X-Real-IP` от Caddy |

Проверки:

```sh
node --test
docker compose config --quiet
docker compose run --rm --no-deps https caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
```
